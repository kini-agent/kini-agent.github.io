Production-minded agent development

AI에게 코드를 맡기는 것이 아니라,
개발 운영체계를 맡깁니다.

DEVOS는 AI Agent가 장시간 자율적으로 작업해도 프로젝트 구조와 품질이 무너지지 않도록 제품 정의, 작업 경계, Capability, 검증, 승인 정책을 Repository 안에 표준화합니다.

5분 안에 시작하기첫 프로젝트 만들기보안 모델

왜 필요한가

AI 코딩 도구를 단순 코드 생성기로 사용하면 매 작업마다 컨텍스트를 다시 설명하게 됩니다. 규모가 커지면 중복 구현, 구조 변경, 테스트 누락, 위험한 자동 실행이 누적됩니다. DEVOS는 대화가 아니라 Repository 자체가 Agent에게 일을 설명하도록 설계합니다.

ProblemPrompt-driven

다음 작업을 사람이 계속 공급하고 세션마다 규칙을 반복합니다.

DEVOSRepository-driven

SPEC, Architecture, AGENTS.md, CURRENT, DoD가 지속적인 컨텍스트가 됩니다.

OutcomeMilestone-level control

사람은 제품 방향과 승인에 집중하고 구현·검증 루프는 Agent가 수행합니다.

핵심 목표: 사용자 명령 횟수는 줄이고, Agent 내부의 구현 → 테스트 → 리뷰 → 수정 → 재검증 루프는 더 길고 엄격하게 만듭니다.

Capability-first Architecture

프로그램을 화면의 집합이 아니라 실행 가능한 Capability의 집합으로 봅니다. Web, Mobile, CLI, MCP, Agent는 동일한 핵심 기능을 사용하는 Adapter입니다.

Quality Gates

자율성이 높아질수록 “완료”를 자연어가 아닌 검사 가능한 조건으로 정의해야 합니다.

TaskFast feedback

관련 테스트를 즉시 실행하고 깨진 상태를 다음 Task로 넘기지 않습니다.

MilestoneFull verification

Build, Type/Lint, Unit, Integration, Architecture를 전체 검사합니다.

ReleaseAudit

보안, 권한, 문서, migration, 운영 리스크를 최종 확인합니다.

Security Model

AI에게 모든 권한을 주는 것이 아니라 허용된 Capability 안에서 최대한 자율적으로 움직이게 하는 것이 목표입니다.

작업기본 정책예
Read자동 허용 가능상태/로그/분석 조회
WriteValidation + 권한Task 생성, 설정 수정
DestructivePreview 또는 승인삭제, archive, rollback
Cost-bearing사람 승인유료 API, Cloud 확장
Production엄격한 승인 정책배포, DB migration
권장: destructive Tool에는 dry-run, idempotency key, request-id, audit log, rollback 또는 보상 전략을 포함합니다.

Enterprise Adoption

전사 도입보다 작은 내부 프로젝트에서 시작해 규칙을 검증한 뒤 단계적으로 확대하는 것을 권장합니다.

1
Pilot

신규 내부 도구 한 개에서 개발 프로세스를 검증합니다.

2
Standardize

AGENTS.md, Architecture, CLI Convention, DoD를 조직 표준으로 만듭니다.

3
Automate

CI에 build/test/architecture/security gate를 연결합니다.

4
Scale

Worktree와 Agent 병렬화를 확대하고 팀별 autonomy policy를 정의합니다.

FAQ

DEVOS는 Agent Framework인가?

아닙니다. 특정 LLM이나 SDK가 아니라 개발 운영 규칙과 프로젝트 구조를 정의합니다. Agent Provider는 교체 가능해야 합니다.

MCP는 필수인가?

아닙니다. 내부 코드에서 Tool을 직접 호출할 수 있다면 MCP 없이도 됩니다. MCP는 외부 Agent/프로세스에 Capability를 노출하는 Adapter입니다.

모든 프로젝트를 하나의 Monorepo에 넣나?

아닙니다. 서로 다른 제품은 독립 Repository를 권장하고, 제품 내부에서만 Monorepo/Multi-module을 사용합니다.

왜 Agent가 DB를 직접 수정하면 안 되나?

권한, Validation, Audit, 재현성과 안전장치가 우회되기 때문입니다. Tool/Service 경계를 통과시켜 blast radius를 제한합니다.
