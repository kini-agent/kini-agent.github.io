# idea

`/idea <만들고 싶은 것>` 로 KINI Dev 프로젝트를 시작합니다.

## 먼저 알아야 할 것

`kini dev agent` 는 실행하지 마세요.
그 명령은 프로젝트 폴더에서 코딩 에이전트를 띄우는 것이고, 당신이 이미 그 에이전트입니다.

`kini dev new` 는 옵션 없이 부르면 사람에게 질문을 던지며 멈춥니다.
반드시 아래의 비대화형 형태로 부르세요.

## 순서

### 1. 세 가지가 있는지 본다

KINI 는 이 셋이 정해지지 않으면 프로젝트를 만들지 않습니다.

- 만들고 싶은 것
- 해결하려는 문제
- 첫 버전에 꼭 필요한 기능

사용자가 던진 한 줄에 셋이 다 들어 있으면 그대로 씁니다.
빠진 것이 있으면 **한 번에 모아서** 묻습니다.
하나씩 되묻지 마세요. 아이디어를 말한 사람에게 취조처럼 느껴집니다.
물을 때는 빈칸이 아니라 구체적인 안을 함께 제시하고, 사용자가 고르거나 고치게 합니다.

### 2. 만든다

```bash
kini dev new "<만들고 싶은 것>" \
  --slug <폴더명> \
  --problem "<해결하려는 문제>" \
  --mvp "<기능, 기능, 기능>" \
  --yes --json
```

`--slug` 는 영문 소문자와 하이픈으로 짧게 짓습니다. 생략하면 아이디어에서 만듭니다.
언어, 플랫폼, 데이터 저장, 개발 모드는 사용자의 profile 기본값을 따릅니다.
사용자가 다르게 말한 경우에만 `--language`, `--platform`, `--db`, `--mode` 로 덮어씁니다.

`--json` 은 stdout 에 결과 한 줄만 남깁니다. 거기서 `root` 를 읽어 다음 단계로 갑니다.

명령이 실패하면 무엇이 빠졌는지 그대로 알려주고 멈춥니다.
없는 것을 지어내서 다시 실행하지 마세요.

### 3. 빈칸을 채운다

만들어진 문서는 뼈대뿐입니다. 그대로 두면 아무 쓸모가 없습니다.

- `docs/SPEC.md` 의 기능 목록을 실제로 만들 수 있는 수준까지 적습니다.
- `planning/ROADMAP.md` 의 M1, M2, M3 을 이 제품에 맞게 다시 씁니다.
- `docs/CAPABILITIES.md` 의 예시 Tool 을 이 제품의 것으로 바꿉니다.

`docs/DEFINITION_OF_DONE.md` 는 완료 기준이므로 손대지 않습니다.

### 4. 보고한다

프로젝트 폴더 경로와, M1 에 무엇을 넣었는지 짧게 말합니다.
그리고 지금 바로 M1 을 시작할지 묻습니다.

코드 스캐폴드는 사용자가 시작하라고 한 뒤에 만듭니다.
`kini dev new` 는 문서와 빈 git 저장소까지만 만듭니다.

## 이미 만든 프로젝트를 이어서 할 때

```bash
kini dev status
```

프로젝트 폴더 밖에서 실행하면 워크스페이스의 프로젝트 목록이 나옵니다.
